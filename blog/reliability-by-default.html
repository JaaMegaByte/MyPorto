Designing Systems That Assume the Network Will Fail

Jun 02, 2026 Reza Dwi Putra 5 min read

Every real-time feature makes a quiet promise: what you see on screen matches what's actually happening. A chat message arrives, a status updates, a bot replies. The moment that promise breaks, because a socket dropped, a request timed out, or two updates arrived out of order, the feature stops feeling real-time and starts feeling broken.

Most of the bugs I've chased in real-time systems weren't logic errors. They were unstated assumptions about the network. That a connection stays open. That messages arrive in the order they were sent. That a retry is harmless. None of those assumptions hold up in practice, and treating them as true is usually where the flakiness comes from.

Start from disconnection, not connection

It's tempting to design the happy path first and bolt reconnect logic on afterward. That ordering tends to produce reconnect logic that feels like an afterthought: a spinner, a generic error, a full page reload. Flipping the order helps. Design what the interface looks like while disconnected and while catching up, then treat the connected state as one case among several rather than the default.

Make retries idempotent before making them automatic

An automatic retry that isn't safe to repeat just turns a dropped request into a duplicated one. Before adding retry logic anywhere, it's worth confirming the operation can run twice with the same input and produce the same result. That single property removes an entire category of "why did this happen twice" bugs later on.

Order is not guaranteed, so stop assuming it

Two messages sent a few milliseconds apart can arrive in either order, especially across reconnects. Systems that quietly assume arrival order matches send order tend to work fine in testing and fail intermittently in production, which is the worst kind of bug to track down. Attaching a sequence number or timestamp to state changes, and reconciling based on that instead of arrival order, removes a lot of the guesswork.

The network isn't a wire that occasionally misbehaves. It's a set of conditions, latency, loss, reordering, duplication, that are always present in some amount.

None of this is exotic. It's mostly about designing for the failure states from the start instead of patching them in once users start noticing. The systems that feel the most solid in practice are usually the ones where someone thought carefully about what happens when things go wrong, not just when they go right.
